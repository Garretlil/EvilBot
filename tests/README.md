# Автоматические проверки

## Быстрые проверки без расходов на ИИ

Из каталога приложения:

```bash
python3 -m unittest discover -s tests -v
```

Или с JSON-отчётом:

```bash
python3 tests/run.py --report /tmp/investor-test-results.json
```

59 тестов и дополнительные варианты входов внутри subTest. Все запросы к провайдеру подменяются; копия приложения, временная база и локальный тестовый HTTP-сервер изолированы от работающего сервиса. Код возврата 0 означает успешный прогон, ненулевой код — ошибку. Зависимости pip не нужны.

Проверяются:

- Пять ходов и запрет шестого; десять уникальных критериев; ровно три действия.
- Расчёт итогов, округление, охват, Н/Д и диапазоны баллов.
- Дословные цитаты, допустимые источники, временной бюджет рекомендаций.
- Невалидный питч, пустые/длинные ответы, некорректный JSON и HTTP-параметры.
- Повторная доставка, конфликт изменённого ответа, конкурентные запросы.
- Сохранение ответа при сбое следующего вопроса и восстановление отчёта после сбоя модели.
- Отсутствие продвижения при повторе старого ответа на фоне более нового сохранённого ответа.
- Изоляция сессий, истечение срока, удаление истории без удаления лимитов.
- Ограничения запросов на браузер, IP и весь сервис.
- CSRF, безопасные cookie, CSP, запрет выдачи .env/исходников/базы.
- Ошибки и тайм-ауты провайдера, повтор невалидного JSON и освобождение слота.
- Инструкция из питча остаётся пользовательскими данными; API-ключ не попадает в тело запроса модели.

## Проверка работающего сайта с реальным DeepSeek

Требует доступного API и расходует токены. Создаёт только собственные тестовые сессии с отдельными cookie и удаляет их после каждого сценария. Не меняет конфигурацию и не очищает чужие данные.

```bash
python3 check_live.py --scenario all
```

Сценарии: обычный питч; попытка навязать 100 баллов/6 вопросов/10 советов; пять ответов «Не знаю» с переходом к новым критериям.

Для проверки через nginx:

```bash
python3 check_live.py --base-url http://127.0.0.1 --scenario normal
```

Лимиты приложения распространяются на эти проверки. Не отключайте ограничения на публичном сервисе ради тестов. Тайм-аут, недоступный провайдер или недостаточный баланс делают live-проверку неуспешной — это не подменяется фиктивным результатом.

## Границы доказательства

Успешные проверки показывают поведение на перечисленных входах. Они не гарантируют устойчивость к любой атаке на ИИ, не подтверждают достоверность бизнес-фактов пользователя и не доказывают качество всех возможных рекомендаций. Тон и содержательная полезность требуют отдельной проверки на новых питчах. Публичный HTTP проверяется отдельно, поскольку облачные сетевые правила находятся за пределами приложения.


## Датасет из кейса

Исходный файл `tests/fixtures/pitch-dataset.md` сохранён без изменений. Парсер и отдельные ожидания для каждой из 15 заявок — в `tests/dataset_cases.py`. Эти ожидания сформулированы командой для тестирования, а не выданы организаторами как эталонные оценки. В работающем приложении нет импорта этого файла, списка проектов или заготовленных вопросов.

Изолированный реальный прогон (нужно разрешение владельца данных на передачу DeepSeek, расходует токены):

```bash
python3 check_dataset.py --phase full --report /tmp/investor-dataset-results.json
```

По умолчанию запускается временная копия сервера с отдельной базой на свободном localhost-порту. Ключ читается из существующего `.env`, не копируется в код или отчёт. Временный процесс и его данные удаляются по завершении. Публичные лимиты работающего приложения не меняются.

Быстрая проверка входа и первого вопроса:

```bash
python3 check_dataset.py --phase acceptance
```

Отдельные заявки:

```bash
python3 check_dataset.py --phase full --ids 04,09,13,14
```

Ожидания: 04 — отсутствует презентация и нет описания; 09 — личная просьба о подготовке вместо проекта; обе отклоняются с понятной причиной. Для остальных 13 заявок проверяется полный раунд. Ответы «Не знаю» сохраняют исходные сведения и не выдумывают новые факты студента. Дополнительно проверяются продажи там, где они явно заявлены/отсутствуют, защита от просьб поставить максимум, источники баллов и переход к новым критериям после отсутствующего ответа.

Результаты сохраняют SHA-256 датасета и кода приложения, вопросы, отчёт и ошибки по каждой заявке. Риск-приоритет и полезность рекомендаций требуют ручной проверки; слова-маркеры не подменяют смысловую оценку.
